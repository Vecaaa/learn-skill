# 跨月大目标的规划参考

用户提出**宽泛、横跨数月**的大目标时读这份（"我想学一年，自己做出 GPT"
"我想系统性搞懂机器学习，最后能自己发论文"）——而不是"教我一个概念"这种单点请求。

这一层套在主循环的第 2 步"出路线"之上，其余步骤（探针→讲解→检验→记账）完全不变。
大目标模式只是多了一层结构，不是另一套教学法。

### 0'. 大目标的澄清比小目标更重要，而且经常要先查一下才问得出正确问题

大目标常常字面上就不现实——用户自己也未必清楚。**"自己做出 GPT-3"** 是个具体例子：
字面上的 GPT-3（1750 亿参数）需要千万美元级算力，不是"学一年就能训出来"的事。
真正可达成、业内公认的对标是理解并实现同样的架构、复现 GPT-2 规模、
搞清楚"再往上扩展到 GPT-3 需要什么"——这才是用户十有八九真正想要的东西。

所以大目标的第 0 步要多问一句、也可能要先做一轮检索才敢问：
**"成功具体长什么样？"**——把它落成一句清楚的 `north_star` 描述，
和"每周大概能投入多久"一起存进 `goals`：

```bash
learndb.py goal add <slug> "<目标名>" \
    --north-star "<拆穿字面理解后、双方都认可的具体成功标准>" \
    --weekly-hours <N>
```

同时要跟用户说清楚：**接下来的计划是里程碑式的，不是日历式的**。
不给"第 9 个月要做什么"这种承诺，因为那大概率是错的——会按实际进度滚动调整。

### 1'. 检索时先看有没有现成的阶梯式项目课程

制定路线前，先查这个大目标是不是已经有人走过、且沉淀成了一条现成的
"build-your-own-X"式阶梯课程（读 `references/domains.md`）。有的话改编它，
优于自己从零拼凑——现成路径已经踩过坑、排过序，重新发明既慢又容易漏东西。

### 2'. 切成里程碑（phase），近详远粗

```bash
learndb.py phase add <goal_slug> "<阶段名>" --seq 1 \
    --objective "<验收标准：到这一步你应该能做什么，不是日期>" \
    --est-weeks <软性估计> --detail detailed
```

**只有当前阶段和下一阶段用 `--detail detailed`**，展开到具体 atom 和 project；
更远的阶段先只给 `seq` + 阶段名 + `objective`（保持默认 `coarse`），
不要提前设计它们的 atom 和项目——大概率会被前面学到的东西改写，提前设计等于白做。

建完第一个阶段后跑 `phase start <id>`：把它设为当前阶段，
并自动把下一阶段标记为可以开始展开（这就是"近详远粗"的滚动实现）。

### 关键规则：路线图必须落库，不能只是聊天里说说

**生成路线图之后，必须真的调用 `goal add` / `phase add` 把它写进数据库**，
不能只在对话里描述一遍就算完事。原因很直接：不落库的路线图这次会话结束就没了，
下次用户回来问"我们上次说好的计划到哪一步了"，你答不出来——整个"跨月计划"这个
功能就名存实亡。检验标准很简单：**用户随时可以说"给我看看路线图"，
你应该能用 `goal roadmap <slug>` 查出来，而不是凭上下文里的记忆现编一份。**

### 3'. 当前阶段内：atom + 巩固项目

当前阶段展开时，除了照常 `add --phase <id>` 建 atom、连 `--prereq`，
每个阶段至少配 1 个巩固项目——这是"不仅要学会知识，还要有成就感"的具体实现：

```bash
learndb.py project add <phase_id> <slug> "<项目名>" \
    --purpose "巩固/应用了哪些 atom" \
    --scaffold "已经帮用户写好的部分，以及为什么（工程量大但不是本阶段要学的东西）" \
    --user-scope "用户自己要设计/写的那一小块，对应哪个 atom" \
    --effort "1-2 次学习会话" \
    --atom <atom_slug> [--atom <atom_slug> ...]
```

**`--scaffold` 和 `--user-scope` 两个字段不能空着**——这是脚手架透明约束：
用户需要清楚知道"这部分是帮你搭好的，你只需要写这一小块"，而不是自己猜。
命令会在缺失时报警告，提醒补上再正式交给用户。

**项目体量的硬护栏**：目标体量是"一到几次学习会话内做完"，不是按大目标总时长
打比例。如果设计着设计着发现规模超了，**处理方式是砍范围**
（做核心切片，完整版本标"可选，以后再做"），**不是延长时间**。

项目做完时：

```bash
learndb.py project done <slug>
```

这会列出项目关联的 atom——**项目完成不等于自动掌握**，要按用户实际写出的
那部分表现，对每个 atom 正常跑 `verify --method transfer`。项目是 atom 走到
"能迁移"这一档最自然的载体，不是绕开检验体系的另一套东西。

### 阶段结束：复盘 + 滚动校准

```bash
learndb.py phase close <phase_id> --retro "<一句话复盘>"
```

这会自动做四件事：记录这个阶段实际花了多久、按"实际/估计"的比值重新校准
所有还没开始的阶段的时间估计（限制在 0.5–2 倍之间防止一次异常把后面全打乱）、
把下一阶段设为当前、把下下阶段标记为可以开始展开细节。

**把重新校准后的估计如实告诉用户，说明这只是参考，不是承诺**。
"一年到底够不够"这个问题的答案会随着阶段推进越来越准，不需要在一开始就装作知道。

### 日常查看进度

```bash
learndb.py goal roadmap <slug>   # 完整树状总览，带各阶段进度
learndb.py status                 # 顶部会带出所有 active 大目标的当前阶段
```
