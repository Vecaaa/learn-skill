## 跨月大目标：先查现成的阶梯式项目课程

SKILL.md「大目标模式」第 1' 步会指回这里。给一个跨月大目标做路线之前，
先查这个目标是不是已经有人走过、且沉淀成了一条现成的阶梯式项目课程——
这三个领域尤其常见：

- **神经网络/机器学习**：Karpathy 的 `micrograd → makemore → nanoGPT / build-nanoGPT`
  就是一条完整的"从手写自动微分到复现 GPT-2"的阶梯，每一步都是可运行的小项目，
  天然满足"分阶段+项目巩固"的要求，直接采纳/按用户基础裁剪即可
- **代码/系统类**："build your own X"系列（自己实现 Redis、自己实现解释器、
  自己实现 Git 等）通常已经把大工程拆成了周级的小步骤
- **读论文/研究方向**：成熟领域通常有公开的课程大纲（见 `research.md` 的
  "抄大纲取交集"），可以直接当阶段划分的骨架

判断标准：**如果搜到的路径已经是"一串可运行的递进项目"，直接采纳它的阶段划分**，
只按用户的基础和每周可投入时间调整每阶段的粒度；只有真找不到现成路径时，
才按 `research.md` 的"取大纲交集"方法自己拼一条。

现成路径的价值不只是省时间——它已经替你验证过"这个顺序学得通"，
自己现编容易漏掉别人踩过的坑（比如某个前置知识点被低估、某两步顺序颠倒会卡住）。

## 代码 / 编程

### 读代码先于写代码（PRIMM）

新手直接被要求"写一个 X"时，语法和逻辑的双重负担会让人卡死。研究支持的顺序是：

```
Predict（看一段代码，先猜它做什么）
  → Run（跑一下，对不对答案）
  → Investigate（逐行/逐块搞清楚为什么是这个结果）
  → Modify（改一小处，观察变化）
  → Make（自己从头写一个类似的）
```

对应到教学循环：一个"写函数"类的 atom，**讲解阶段就该是前三步**，
**检验阶段用 Modify 或 Make**。不要跳过 Predict 直接讲代码——
"先让用户猜"这个动作本身就是主动检索，比直接讲有效。

### 专家读代码的路径，直接教给用户

研究发现专家和新手读代码的路径系统性不同：**新手线性地从头读到尾**；
**专家自顶向下**——先看抽象接口/函数签名/类结构，搞清楚"这一层在干什么"，
再决定要不要深入某个实现细节。

这个差异可以直接当作显式技巧教给用户，而不只是让他们自己悟：
> "先别读函数体，看这几个函数名和参数，你觉得整个模块想干什么？"

对应到 atom 设计：教一段复杂代码时，先建对应"接口层"的 atom（这层负责什么），
再建"实现层"的 atom（怎么实现的），依赖边从实现指向接口。

### Notional machine：先建执行模型这个锚点

教一门语言或一个系统时，用户脑子里需要一个"这东西是怎么被执行的"的简化模型
（不必完全准确，但要自洽）——例如"JS 的作用域链""Python 的引用计数"。

**这个模型本身应该是路线图里最早的几个 atom 之一**，且值得反复当锚点引用。
没有它，后面所有"为什么会这样"的追问都没有落脚点。

### Subgoal labeling：给代码块打目的标签

worked example 不要只逐行注释"这行做了什么"，而是**按目的分组打标签**：

```python
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1        # ── 初始化搜索范围
    while lo <= hi:
        mid = (lo + hi) // 2         # ── 取中点
        if arr[mid] == target:       ┐
            return mid                │ ── 判断命中/继续哪一侧
        elif arr[mid] < target:       │
            lo = mid + 1              │
        else:                         │
            hi = mid - 1             ┘
    return -1                        # ── 未命中
```

比逐行讲解更利于用户把代码组织成"意图块"而不是一串孤立语句，
后续复述和迁移都会更容易。

### Tracing：用外部变量表，不要口头讲执行过程

讲"这段代码怎么跑的"时，画一张表比连续说话有效得多——新手的工作记忆
装不下"同时跟踪三个变量随时间变化"：

| 步骤 | lo | hi | mid | 命中? |
|---|---|---|---|---|
| 1 | 0 | 9 | 4 | 否，偏小 |
| 2 | 5 | 9 | 7 | 否，偏大 |
| 3 | 5 | 6 | 5 | 是 |

讲解阶段直接画这张表，检验阶段让用户自己填空。

### Debug 检验：用"讲给我听"代替"你看哪错了"

对 `debug` 方式的检验，比起直接问"这段代码错在哪"，更有效的形式是
橡皮鸭式的：**"你逐行跟我解释一下这段代码在干什么。"**
错误理解会在用户自己复述的过程中自己暴露——这本身既是检验也是练习，
用户经常讲到一半自己发现问题。

### Parsons 题：写代码前的过渡检验

用户刚学完语法、还没自信独立写代码时，**把代码打乱成块让用户排序**
（不用管具体怎么敲字符），比直接要求写代码门槛低得多，且对逻辑的检验强度
不打折。适合放在 `judge`/`predict` 和真正的 `Make` 之间当过渡。

## 神经网络与机器学习

### 代码和直觉优先于数学推导

对有编程背景的用户，先给能跑的最小代码（哪怕只有几十行的手写反向传播），
再讲数学，效果明显好于反过来。**这正好是"讲解顺序：具体→一般"原则
在这个领域最具体的应用**——数学推导才是最后一步的"一般化规则"，不是入口。

手动实现一遍反向传播（不调库）建立的直觉，比看懂数学公式更持久，
因为它把"梯度怎么流动"变成了用户可以跟踪的具体计算过程，而不是符号操作。

### Whole game：先跑通完整模型，再逐层剥开

不要因为"用户还没学完线性代数/概率论"就拒绝让他碰一个完整能跑的模型。
更有效的路径是：先跑通一个"能看到结果"的完整流程（哪怕黑箱），
用户会自己在过程中感知到"这里我不懂"，这些感知直接变成待补的前置 atom。

对应到 atom 设计：**不强制要求路线图上所有前置数学 atom 全部学完才开始模型部分**。
可以先建一个"跑通一个模型"的 atom（level 要求较低），
再从用户实际卡住的地方反向长出数学前置。

### 训练过程可视化优先于看 loss 数字

如果用户在学的东西涉及"训练动态"（loss 下降、预测变化、注意力分布等），
优先建议/使用可视化而不是让用户盯 loss 数字——固定一个测试样本，
观察模型预测随训练变化，比抽象的数字曲线更能建立直觉。

如果用户环境允许可视化输出（图表、交互式页面），这类内容优先用图而不是文字描述，
对应 `pedagogy.md` 降维梯里的 L5"换表征"。

### 交互式解释作为教学素材

这个领域有一批公开的高质量交互式讲解（distill.pub 的技术文章、3Blue1Brown 的
可视化系列、Karpathy 的 nn-zero-to-hero 系列、CNN Explainer 等）。
它们把"改变模型/参数，立刻看到结果变化"做成了可交互的页面，
对建立直觉的效果通常好于纯文字讲解。

**用法**：当某个 atom 卡在"看不出这东西的行为规律"时，
优先检索是否有对应的交互式讲解可以推荐，而不是继续用文字类比硬讲。
检索前判断这属于"稳定知识"（这类经典交互讲解通常几年都不过时），可以放心引用。

## 读论文

"学会读某领域的论文"不是一个孤立技能，是**知识框架 + 阅读策略**的结合：
路线图里该会的 atom 还是得先会，阅读方法只是加速器，不是替代品。
不要把"教读论文"简化成只教一套阅读技巧。

### Keshav 三遍法

| 遍数 | 做什么 | 目的 |
|---|---|---|
| 第一遍（5-10 分钟） | 标题、摘要、图表、小标题、结论 | 判断这篇值不值得往下读 |
| 第二遍 | 引言、结论、通读全文但跳过细节证明 | 抓住内容，不抓细节 |
| 第三遍 | 逐字读，重现作者的推导/实验 | 真正的深度理解，能挑出问题 |

配合 **5C 评估框架**（读完至少能回答）：
category（这是什么类型的工作）、context（跟哪些已有工作相关）、
correctness（假设站得住脚吗）、contributions（真正的贡献是什么）、
clarity（写得清楚吗）。

### Andrew Ng 变体：先建清单再深入

进入一个新方向时，不要按顺序逐篇通读。先列 5–10 篇候选，
每篇只花第一遍的时间（约 10%），基于这轮筛选决定哪些值得精读。
这个变体更适合"用户要系统性搞懂一个新领域"而不是"读手头这一篇"的场景。

### 检验设计

精读（第三遍）之后的检验不要用"这篇论文讲了什么"（太模糊，等于没测）。
用具体的 `predict`/`debug` 题：

> "如果去掉这篇论文的某个关键假设，实验结果会怎样变化？"
> "这个消融实验为什么要做，去掉它整篇论文的论证会缺什么？"

这类题比复述摘要更接近 `transfer` 强度，且能测出用户是不是真的理解了
论文的因果结构，而不是记住了摘要的措辞。

### 和知识库的配合

读论文过程中遇到的每个"没见过的技术/概念"都值得立刻 `add` 成新 atom
（哪怕先不深挖），挂上 `--source` 指回这篇论文。攒够几篇之后，
用户会有一张具体是从哪些论文里长出来的知识地图，比读完就忘有用得多。
