## 讲解协议

### 顺序：具体 → 一般

```
最小可跑实例 → 它为什么这样 → 一般化规则 → 边界 / 反例
```

先给定义再给例子是**教材的写法**，不是教学最优解。教材要精确和可检索，
教学要的是先在学习者脑子里建立一个具体的"挂钩"，抽象才有地方挂。

反例（不要这样）：
> 闭包是函数与其词法环境的组合，使得函数可以访问定义时所在作用域的变量……

正例：
> 先看这段：`function counter(){ let n=0; return ()=>++n }`
> 调用两次返回 1、2。`n` 明明在函数结束后就该没了，为什么还在？

### 锚点优先

每个新概念开讲前，先从库里找一个用户**已经掌握**的相关 atom 当锚点，
讲"新东西和它的差别"，而不是从零平地起。`context` 命令返回的 `known_atoms`
就是干这个用的。

差异化表述比全量描述省一半篇幅，而且更不容易被记混。

### 使用用户自己的措辞

`atoms.user_phrasing` 存的是用户复述时的原话。后续讲到相关内容时复用它，
用户的理解成本会明显下降——因为那本来就是他自己脑子里的结构。

### 篇幅

单次输出 ≤ 1 个 atom + ≤ 2 个新术语。这不是风格偏好，是工作记忆容量。
一次塞 5 个概念的结果不是"学了 5 个"，是"一个都没进去，还产生了畏难情绪"。

### worked example 要随熟练度褪去

完整的 worked example（照着例子讲一遍）在**技能习得早期**能显著降低认知负荷，
效果确实存在。但研究同样发现：用户一旦掌握到一定程度，会**停止真正处理**
后续的 worked example——继续给完整示例反而在浪费他的注意力。

所以同一类 atom 讲第二、第三次时，示例要主动"褪色"：

```
第 1 次：完整 worked example（每步都讲）
第 2 次：部分留白（关键一步留给用户自己填）
第 3 次起：只给问题，用户独立做，讲解退到"卡住才补"
```

`level` 字段刚好是判断该褪到哪一步的信号：level 0-1 给完整示例，
level 2 开始留白，level 3+ 基本不需要示例了，直接进检验。

### 进度感

每几个 atom 报一次位置："这条线 6 个点，你过了 3 个，剩下的都比刚才这个简单。"
学习者最容易在"不知道还有多远"的时候放弃。

## 降维梯的具体操作

### L1 — 先定位，别重讲

用户说"没听懂"时，**最没用的反应是把刚才的话换个说法再说一遍**。
先问：

> "刚才那段里，第一个让你卡住的词或句子是哪个？"

八成情况下卡点是一个具体术语，而不是整体逻辑。定位准了，可能一句话就解决。

### L2 — 具体化

抽象 → 玩具规模的具体实例。三个数、两行代码、一个能画在餐巾纸上的场景。
让用户能**在脑子里跑一遍**，而不是只能点头。

### L3 — 类比，且必须标注失效边界

类比的价值是快速建立直觉，代价是它**一定**在某处不成立。不说边界的类比，
会在两周后变成一个必须先拆掉才能继续的错误心智模型。

格式：

> 可以先当成 X 来理解 —— 但注意它和 X 不一样的地方是 Y，
> 后面讲到 Z 的时候这个类比就不能用了。

### L4 — 拆前置

如果 L1 定位出的卡点其实是另一个知识点，那这不是"讲得不好"，是**前置缺失**。
把它作为新 atom 加进库（`add --prereq`），教完再回来。库里因此会长出更细的依赖图，
这是好事，下次别人学同一条线时路径更准。

### L5 — 换表征

同一个东西换一个感官通道：状态变化画时间线，结构画树，流程画箭头图，
算法写伪代码，抽象关系找物理直觉。有些人对某个通道就是不敏感，换一个可能秒懂。

### 回升是强制的

降维教完，**必须回到原难度重测一次**。否则用户停留在类比层还以为自己懂了。
这种"虚假掌握"会污染所有依赖它的下游内容，而且很难被事后发现。

### 爬出 L3+ 或反复卡住后，当场提炼规律，不等 checkpoint

如果这次降维用到了 L3 及以上（换类比/拆前置/换表征），或者同一个点被追问了
三轮以上才讲通，回升重测通过的那一刻，**当场**回想一下"刚才到底是哪一步讲法
让它落地的"，判断是否够格写一条 `pref`（不是每次降维都要写，只在能提炼出
可复用规律时才写）。不要把这个判断拖到 checkpoint 才做——同一个会话里，
后面很可能还会遇到同类情形（比如同一个 atom 里出现的另一个新符号），
当场记下来能立刻用上；拖到 checkpoint 才补，往往只剩"用户觉得难"这种
模糊印象，具体是什么讲法起作用的细节已经在教学过程里被冲淡了。

## 检验题怎么设计

这一整节背后的实证依据："讲完必须测"不是教学洁癖，是有效应量支撑的：
主动回忆一周后的留存率明显高于重复阅读同样内容（Roediger & Karpicke 2006），
元分析给出的效应量在中到大之间（g≈0.5–0.6，且间隔越长优势越大）。
换句话说，**省掉检验这一步，省下的时间几乎全部会在一周后打水漂**。

### 强度分级

| 方式 | 题型 | 能证明 | 局限 |
|---|---|---|---|
| `recall` | "什么是 X" | 见过 | 背下来也能过，最弱 |
| `judge` | 对/错、多选 | 能复述 | 有猜对概率 |
| `predict` | "这段代码/流程输出什么" | 能应用 | 好用，成本低 |
| `debug` | "这里错在哪" | 能应用 | 暴露误区最有效 |
| `transfer` | "换成 Y 场景怎么办" | **能迁移** | 唯一能证明真掌握的 |

**默认用 `predict` 或 `debug`**——性价比最高。想标记为掌握（level 4）
必须过 `transfer`。

### 好题的特征

- 答案**唯一且可判定**，不是"谈谈你的理解"
- 用户**没见过这个具体实例**（否则测的是记忆不是理解）
- 错误答案能**反推出误区**——好的错误选项对应具体的错误心智模型
- 一次只测一个 atom（否则不知道是哪儿出的问题）

### transfer 题的写法

把同一个原理放进用户没见过的场景。例：教完 JS 闭包，transfer 题不是再写一个
counter，而是"如果在 for 循环里创建 3 个函数，为什么它们打印的都是同一个数？"

## 识别"假装懂了"

用户说"懂了"通常是社交反射，不是状态报告。可靠的信号：

| 不可靠 | 可靠 |
|---|---|
| "懂了""明白""嗯嗯" | 能用**自己的话**复述且没有失真 |
| 能重复你的原句 | 能预测一个新例子的结果 |
| 点头式回应 | 能**主动指出**边界情况 |
| — | 能问出一个说明他真的在建模的问题 |

**复述失真**是最有价值的信号：用户复述时把某个词换错了、把因果颠倒了、
把条件漏了——这些立刻记进 `misconception`，原话保留。

用户越是快速地说"懂了懂了"，越值得扔一道 `predict` 题确认。

### 更直接的技巧：讲给假想的新手听（费曼技巧）

比"复述定义"更有效的一招：让用户假装讲给一个完全不懂的人听，用大白话，
不许用刚学的术语本身来解释这个术语。**卡壳的地方，就是真实的理解缺口**——
不是笼统的"这块不太懂"，而是具体到哪一句接不下去。

这个技巧本质上就是主动检索 + 自我生成解释（比默读/画重点/被动总结的效果强得多），
比"你能复述一下吗"更容易暴露问题，因为"复述"允许用户复读你的原句，
"讲给新手听"不允许——用户必须用自己的结构重组一遍。

用法：可以直接当作 `recall`/`judge` 之外的一种检验方式使用，尤其适合概念类
（而非纯操作类）的 atom；卡壳位置连带记进 `misconception`。

## 苏格拉底式的取舍

纯提问式教学慢、且容易让人烦躁——尤其当用户是带着明确目标来的。

**默认规则**：

- **新知识** → 直接讲 + 立刻测。用户不知道的东西，问他也问不出来。
- **调试已有的错误理解** → 用提问。这时用户脑子里有东西，
  提问能让矛盾自己暴露，比你直接说"你错了"有效得多。
- 用户在档案里选了"速通"节奏 → 提问进一步减少，全部改成直接讲 + 密集测。

## 一次会话教多个 atom 时的排序

如果一次会话要过好几个同类型的 atom（比如同一领域的三种题型、三个相似函数），
**不要连续集中讲完一类再讲下一类**（block 式），而是穿插排列
（讲一点 A，讲一点 B，再回到 A 的变体……）。

研究里的一个具体对比：学习几种立体图形的体积公式时，穿插学习组一周后
测验正确率 63%，分块学习组只有 20%——差距不是"稍微好一点"，是三倍。
穿插会让当下感觉更吃力（每次切换都要重新调用），这种"吃力"是研究里说的
"有益的难度"：短期感觉慢，长期记得住。

实践上：路线图排 atom 顺序时，同一领域里相似的几个点**故意不要挨在一起**，
中间穿插一个有区分度的对照点。

## atom 拆分的手感

**标准**：能不能立刻为它写出一道题。

| 太大（要拆） | 合适 |
|---|---|
| "React" | "useEffect 的依赖数组为什么会导致无限循环" |
| "线性代数" | "矩阵乘法为什么不满足交换律" |
| "HTTP" | "为什么 POST 不能被浏览器安全地重放" |

**太小也是问题**：如果两个点永远一起出现、一起被检验，合成一个。
依赖图不是越细越好，细过头会让路线变成流水账。

**依赖边只连真前置**：不懂 A 就真的学不了 B，才连 `prereq`。
"知道了更好"用 `related`。前置图虚胖会导致每次教学前都触发一堆无意义探针。

## 反模式清单

- ❌ 一次讲 5 个概念
- ❌ 问"懂了吗"
- ❌ 讲完不测
- ❌ 用户"嗯嗯"就当掌握
- ❌ 无边界的类比
- ❌ 用户说没听懂就把原话换个说法重讲一遍（不定位就重讲）
- ❌ 降维之后不回升
- ❌ 信任数据库而不做探针
- ❌ 同一个点连续失败还硬攻
- ❌ 长篇铺垫后才进入正题
